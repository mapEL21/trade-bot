# Контекст Trade Bot для совместной работы

Обновлено: 11 октября 2026. Перед работой сверяй этот файл с `git status` и фактическим кодом: несколько помощников могут работать в одной папке. Полная история решений и обсуждений — `docs/DIALOGUE_SUMMARY.md`.

## Цель и договорённости

Разрабатываем локальное приложение для исследования и последующей автоматической торговли криптофьючерсами. Интерфейс и общение — на русском, понятные пользователю без подготовки разработчика. Сообщения коммитов — на русском. Репозиторий: https://github.com/mapEL21/trade-bot, основная ветка `main`.

Сейчас задача инженерная: сбор публичных данных, анализ, воспроизводимые проверки стратегий и реалистичная симуляция исполнения. Пользователь хочет в будущем живую симуляцию, а затем малый реальный счёт. Исполнительный торговый адаптер пока не реализован. Не обещаем прибыль и не меняем критерии ради красивого бэктеста. Цель первого счёта около 10 USDT — проверка механики, не доказательство доходности.

Исследование поддерживает любую пару разных площадок из Hyperliquid, Binance, Bybit, OKX, только общие инструменты с прямым соответствием. Hyperliquid — DEX со стаканом. Мемкоины и создание токенов не входят в текущий план.

Планируемое исполнение — X Binance через TigerX. Совместимость API, фактические комиссии, ограничения аккаунта и применимость скидки к API ещё не проверены. На скриншотах пользователя были базовые фьючерсные комиссии maker 0,02%, taker 0,05% и снижение на 45%; нельзя считать это подтверждённым эффективным тарифом. В симуляции комиссия задаётся явно; 5 б.п. за сторону — пример.

Разработка адаптеров, интерфейса подключения, тестов и контроля риска — часть проекта. Она не требует самостоятельно вводить реальные секреты или совершать сделки. Реальная отправка ордеров — отдельный будущий этап с явным разрешением пользователя; сегодня все проверки без торговых ключей.

## Архитектура и основные файлы

- `src/` — React + TypeScript + Vite. `Research.tsx` — запись, выбор площадок и поиск общей пары; `ResearchAnalysis.tsx` — отчёты записей; `StrategyReplay.tsx` — настройки и результат стратегии. `api.ts` — запросы к локальному API.
- `server/TradeBot.Api/` — ASP.NET Core (.NET 10). Локальный API, SQLite для рабочего пространства. Карточки ботов — черновики, торговля через них не запускается.
- `server/TradeBot.Recorder/` — публичные WebSocket-потоки, CLI и библиотека для API. `RecorderOptions.cs` — каналы, `MarketWire.cs` — классификация, `MarketCatalog.cs` — инструменты, `CaptureFile.cs` — очередь и запись.
- `MarketResearch.cs` — управление записью и обновления интерфейса; `MarketQuote.cs` — только BBO. События глубины не освежают возраст BBO.
- `RecordingAnalysisStore.cs` — безопасное чтение записей и сохранение отчётов, один расчёт одновременно.
- `MarketAnalysis.cs` — оценка качества данных, реакции цены и условных BBO-сделок.
- `StrategyReplay.cs` — стратегия `leader-lag`, симуляция на записи.
- `ReplayDepth.cs` — новый разбор стакана, правила размера заявки и модель исполнения. Детали — `docs/STRATEGY_REPLAY.md`.
- `server/TradeBot.Api.Tests/` — xUnit, включая API-тесты. `tests/browser/research.spec.ts` — Playwright, мобильная ширина и axe. `tests/*.test.ts` — модель интерфейса.

## Записи и причинность

Записи находятся в `server/TradeBot.Api/data/market/` (путь настраивается через `Market:Path`), не коммитятся. Каталог: `yyyyMMddTHHmmssZ-guidN`.

- `manifest.json`: схема 3, параметры, частота Stopwatch, метаданные инструментов обеих бирж; поддерживается чтение старых схем 1 и 2.
- `events.ndjson`: `Source`, `Connection`, `Kind`, `ReceivedUtc`, `ReceivedTicks`, исходный JSON `Payload`.
- `summary.json`: завершение, ошибки, разрывы, счётчики и очередь.
- `analysis-v1.json` и `strategy-replay-v1.json`: отдельные последние отчёты. Повторный расчёт заменяет только соответствующий отчёт.

Порядок — локальный `ReceivedTicks`, затем номер строки. Источник и биржа исполнения могут поменяться после выбора поводыря. Запрещено использовать будущие котировки, глубину или результат для принятия более раннего решения. Виртуальная заявка исполняется перед событием с равным временем. Глубину нельзя подменять неограниченной ликвидностью BBO при ошибке.

Записываются: Binance `bookTicker` и `depth20@100ms` (снимок верхних уровней); Bybit `orderbook.1` и `orderbook.50` (snapshot/delta); OKX `bbo-tbt` и `books5` (объём в контрактах); Hyperliquid `bbo`, `l2Book`; также публичные сделки. Это ограниченная, а не полная глубина рынка.

Регистратор исправлен после переполнения очереди на всплеске: до 8192 событий и 32 МиБ оценочного буфера, неблокирующий приём, явная ошибка при переполнении. Не скрывать потерю данных. Остановка записи замораживает возраст BBO в интерфейсе.

## Первая стратегия

Первые 120 с по умолчанию — калибровка: импульс 3 б.п. за 250 мс, реакция другой биржи через 100 мс; минимум 10 наблюдений каждого направления, положительная реакция и преимущество 0,5 б.п. Затем поводырь и медианный базис фиксируются. Это эвристика, не доказательство причинности.

Дальше 8 независимых сценариев: по импульсу / против импульса × 10/25/50/100 мс задержки. Против импульса — контроль на тех же сигналах, не готовая стратегия разворота. Отставание должно покрывать заданные расходы и запас; одна позиция/заявка одновременно. Выход по сближению, развороту, стопу или времени; задержка действует на обе стороны. Разрыв/устаревание при открытой позиции означает неполный результат, не фиктивное закрытие.

В v0.1 исполнение только BBO. Текущая доработка v0.2 добавляет номинал, шаг и минимальный размер, ограничение цены, среднюю цену по уровням, частичный вход/выход и денежный итог закрытых сделок. Старый BBO-режим остаётся явно упрощённым. Метаданные берутся из записи, не из сегодняшнего API. Для OKX контракты переводятся через `ctVal` (поддерживается линейный USDT, `ctMult=1`). Минимальные 10 USD Hyperliquid — явно отмеченное допущение по документации, не историческое поле записи.

Номинал заявки не равен балансу или марже. Плечо, funding, ликвидация, maker-очередь и индивидуальные правила брокера ещё не моделируются. С v0.2.1 выход, не уложившийся в предел цены, повторяется новой заявкой на остаток, и сделка закрывается по средней цене всех частей: иначе худшие выходы выпадали из статистики. Только если исполнение за записанной глубиной неизвестно, сценарий прекращается, остаток показывается, вся незакрытая сделка исключается из итогов закрытых сделок.

v0.3.0 добавляет вход maker (`entryOrder`, `makerFeeBps`, `makerWaitMs`; по умолчанию taker): post-only заявка по своей лучшей цене, исполнение только когда встречная цена дошла до её уровня, выход taker. Это осознанно консервативная модель без очереди; доля исполнений «N из M» — главный показатель. Подробности — `docs/STRATEGY_REPLAY.md`.

v0.3.1: задержка 10/25/50/100 мс — время от отправки заявки до исполнения на бирже. Все условия входа проверяются только в момент сигнала; отправленная заявка исполняется на зафиксированных условиях, без повторной оценки выгоды. Отмена — только отдельным запросом со своей задержкой. Потеря данных ведомой биржи или неизвестная глубина при заявке в пути — неопределённый результат, не отмена.

v0.3.2: виртуальное время не идёт назад (повтор выхода больше не перезапускает лимит удержания). Конец записи, разрыв или устаревание данных при отправленной/выставленной заявке — неопределённый результат. Maker в модели стакана — экспериментальная: исполнение = записанные сделки агрессора по цене заявки или хуже минус видимая очередь перед ней (`ReplayTradeParser` в `ReplayDepth.cs`, сделки из потоков `*-market` / Hyperliquid `trades`); без записанных сделок maker по стакану не считается.

На пользовательской 10-минутной записи MAGIC Binance/OKX v0.1 выбрала Binance поводырём, но отфильтровала все входы по расходам. Это наблюдение, не повод автоматически снижать комиссию или подгонять пороги.

## Запуск и проверки на Windows

- Двойной клик `Запустить Trade Bot.cmd` запускает API и сайт, открывает браузер. `Остановить Trade Bot.cmd` штатно завершает запись и останавливает только процессы этого запуска.
- Реальные порты: UI 5173, API 5080. Служебные PID и журналы: `artifacts/launcher/`. Не завершать все процессы node/dotnet по имени.
- Перед сборкой .NET остановить наш сервер, предварительно проверив отсутствие активной записи: работающий API блокирует DLL. Для автоматизированного запуска: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/windows-launcher.ps1 -Action Start -NoBrowser`; остановка — `-Action Stop`.
- `node scripts/dotnet.mjs test TradeBot.slnx` — сборка и серверные тесты; wrapper ищет локальный `.tools/dotnet`.
- `pnpm build` — проверка TypeScript и сборка UI; `pnpm test` — тесты модели.
- `$env:PLAYWRIGHT_CHANNEL='msedge'; node node_modules/@playwright/test/cli.js test tests/browser/research.spec.ts` — браузерные тесты; сначала собрать API. Отдельные порты 5081/5175 и данные в `artifacts/`.
- У пользователя в обычном PowerShell может не быть node/pnpm/dotnet в PATH. Launcher находит локальные инструменты; не ломать эту возможность. Node может быть в `$env:USERPROFILE/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node.exe`.
- `node node_modules/prettier/bin/prettier.cjs --write <files>` — форматирование TS/Markdown.

## Совместная работа Codex и Claude Code

Коммиты — один на законченный этап: код, тесты и документация вместе, после прохождения проверок; не дробить одну задачу на несколько коммитов подряд. Затем отправка в `main`. Не отменять чужие незакоммиченные изменения. Не редактировать одни файлы одновременно без распределения. Папка `.claude/` появилась со стороны пользователя; не включать её настройки в коммит автоматически. Секреты, записи, `.tools`, `artifacts`, БД и логи не публиковать.

Ближайшее поручение Claude: независимое ревью v0.2, сначала без изменения файлов. Прочитать `git diff`, `ReplayDepth.cs`, `ReplayDepthTests.cs`, `StrategyReplay.cs`, `RecordingAnalysisStore.cs` и интерфейс. Проверить причинность, Bybit snapshot/delta и сброс, OKX единицы, округления/минимумы, ограничение цены, частичное исполнение, комиссии и совместимость старых отчётов. Возвращать конкретные дефекты: файл/строка, воспроизведение, последствия, предлагаемая правка. Не менять настройки ради прибыльного результата. Codex завершает реализацию и проверки, затем разберёт замечания.

Следующие этапы после этой доработки: независимые записи и проверка фиксированных правил, живой paper trading, затем отдельная верификация TigerX API/комиссий и торговый адаптер с контролем риска. Не обозначать эти будущие этапы как готовые.

ECC — набор применяемых по задаче инженерных навыков; этот файл — память проекта. Они решают разные задачи и могут использоваться вместе.
